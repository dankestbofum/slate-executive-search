# Authentication and invitation audit — 2026-09-22

Scope: source at `a6c91bf`, the offline browser fixture in this directory, and current Clerk documentation. No real invitation ticket, account, credential, or production record was used. The user's deployed observation is a `/join/sign-in?__clerk_status=sign_in&__clerk_ticket=…` page with the Slate heading and an empty Clerk panel. I did not independently inspect that ticket or its browser console, so the fixture demonstrates a matching failure mode, not proof that the deployed session was pending.

## P1 — A pending Clerk session produces an empty invitation panel

**Reproduction:** `node docs/audits/2026-09-22-pilot-walkthrough/auth/reproduce-pending.cjs` starts the real Express app against temporary data, signs a fixture JWT with `sts: pending`, and supplies a browser SDK stub whose session has `currentTask.key === 'choose-organization'` and a present user. It observed `/api/me` returning `401 SESSION_TASK_PENDING`; the browser rendered the invitation heading and `<div data-clerk-auth="sign-in">` with zero children; `mountSignIn` was never called. The test exits 0 when those assertions hold. This is an **offline simulated Clerk state**. It does not validate the hosted Clerk SDK, its ticket handling, or the actual deployed session.

**Cause in the audited source:** `server/auth.js:247-251` returns a task-specific 401 before resolving the user. On first boot, `public/app.js:2225-2229` leaves `state.user` null and returns false. `public/app.js:2699` therefore emits a sign-in mount target, but `public/auth.js:115` mounts it only when `!clerk.user`. `public/app.js:9628` renders that state. The header sign-out control is inside the collapsed public menu, so the panel can appear to offer no usable next step. This is consistent with the reported blank, but the hosted cause remains unconfirmed without a redacted console/session-state capture. Clerk documents pending sessions and the need to display the current task in its [session tasks guide](https://clerk.com/docs/guides/configure/session-tasks). Its [JavaScript task component reference](https://clerk.com/docs/js-frontend/reference/components/authentication/task-choose-organization) shows `mountTaskChooseOrganization()` for an interrupted `choose-organization` task.

**Fix:** Represent a pending task explicitly in the client. When `clerk.session?.currentTask` exists, render the matching Clerk task component or a supported custom flow, with a visible recovery path for unknown tasks. Do not route a pending session back through the normal sign-in target. Choose task URLs/redirects that return to `/join` after completion. Keep Slate data routes closed until Clerk makes the session active. The current `pendingTask` getter in `public/auth.js:35` already exposes the key but is unused by the renderer. Cover at least organization selection, password reset, and MFA if those tasks are enabled in the Clerk instance. Clerk says sign-in/up components handle tasks during uninterrupted flows; explicit handling is needed when a pending session returns to an app route.

## P1 — Pending task cannot use Slate's own workspace chooser

`public/auth.js:26-33` says Slate will handle organization choice in its own UI, yet `server/auth.js:247-251` denies `/api/me` and `/api/organizations` for every pending session. `public/app.js:2225-2229` sets an onboarding stage without a user or workspace list. Consequently the app's chooser has no authenticated identity or organization list to display. The task has to be completed through Clerk's pending-session API/UI, or a deliberately scoped pending-session endpoint would need to be designed and tested. A generic 401 retry or “check invitations” does not break this loop.

## P2 — Session-task changes are not observed unless session or organization ID changes

`public/auth.js:54-69` invokes client callbacks only when `session.id` or `organization.id` changes. Task/status can change within the same session. If Clerk's task component does not navigate, the client can retain a stale pending view. Track `session.currentTask?.key` and status transitions or navigate explicitly on task completion. Verify both same-ID completion and organization selection in a real development Clerk instance. The existing browser stub in `tests/browser/clerk.js:129-177` always creates an active session with `currentTask: null`, so `tests/browser/invitations.spec.js` does not exercise this state.

## P2 — Ticket-only legacy redirects lose the assigned-search destination

The default invitation URL built by `server/index.js:3410-3415` includes the target organization and search. An operator override (`SLATE_INVITATION_REDIRECT_URL`) returns unchanged, and legacy links may contain only Clerk's ticket and status. After authentication, `public/auth.js:118-127` builds `/join` from only `organization` and `search`; `public/app.js:2279-2283` sends a user without both IDs to workspace Home. The ticket is correctly preserved until Clerk handles it, but the app cannot infer which search to open from that bare URL. Where there is exactly one **verified, active** workspace and one assigned search, it can guide the user there after the session is active; otherwise show a chooser. Never derive access from the ticket string or a query parameter. `README.md:233-240` already advises leaving the redirect override unset for the standard flow.

## Validation gap and pilot gate

`tests/browser/invitations.spec.js:6-24` verifies ticket retention and mount props against an SDK stub; `tests/clerk-auth.js:160-164` verifies the server's pending 401. Neither checks the combined browser state. `docs/pilot-runs/2026-09-21-release-readiness.md:283` explicitly records the 12-case real-Clerk rehearsal as **not run**. Before an invitation pilot, run new and existing account invitations, pending organization choice, interrupted password/MFA task if enabled, wrong-account recovery, accepted/revoked links, and assignment landing in a Clerk **development** instance with test addresses. Also check the deployed page's redacted console/network failures and whether the actual Clerk session has a current task; no ticket value should enter logs or evidence.

Clerk's [organization invitation guide](https://clerk.com/docs/guides/organizations/add-members/invitations) says a custom redirect page must handle authentication and may embed SignIn. The [JavaScript SignIn reference](https://clerk.com/docs/js-frontend/reference/components/authentication/sign-in) notes that its component cannot render for an already signed-in user in a single-session app. The current code's `!clerk.user` guard is thus reasonable for a completed session but requires a separate pending-task path.

## Local fix status after the baseline audit

The subsequent working-tree changes in `public/app.js`, `public/auth.js`, and `server/index.js` address the reproduced client state: a pending session now has a task screen, task/status transitions trigger a refresh, and an organization task lists Clerk memberships and invitations without a create-organization button. Sign-in completion only auto-continues when the target matches a verified membership; opaque ticket links keep the chooser. Search navigation is derived from the server-authorized search list after the workspace becomes active. Fresh same-origin invitation redirects to Home are upgraded to `/join` with organization/search context. The non-pending error path also clears the pending flag. These are **local source changes**, distinct from the baseline reproduction above, and have not been validated with Clerk's hosted SDK or a real development-instance ticket in this audit.

One configuration gate remains: hiding creation in Slate's task screen does not disable Clerk's own frontend Organization creation API. Clerk says user-created Organizations are allowed by default and creators receive an admin role; if the production Clerk instance permits that, a user can bypass Slate's founder allowlist by creating an Organization directly with Clerk. Confirm that user-created Organizations and automatic first-Organization creation are disabled for invitees, or enforce the founder policy when Slate accepts a newly created Organization membership. See [Clerk Organization settings](https://clerk.com/docs/guides/organizations/configure). The new browser regressions use a stub and cannot establish this instance setting or that pending-session membership/invitation reads work against hosted Clerk.
